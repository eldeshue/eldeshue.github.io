## 추상화
Vulkan은 복잡한 api이며, 추상화에 대한 욕망을 불러일으킴.

그러나, 성급한, 잘못된 api 추상화는 많은 문제의 근원이 되기에 좋은 선택이 아님.

따라서 되도록 이런 **추상화 욕구에 저항**하기 바람.

추상화를 한다고 하더라도, 가능한 Simple하게 유지하는 것이 바람직함.

### 추상화 팁
- **구현하고자 하는 응용프로그램의 목적이 추상화를 유도하는 상황이 가장 좋음.**
- Vulkan의 모든 기능을 제공하려고 하지 마라 -> 매우 중요한듯, 주된 사용 대상에 추상화
- 조합론적으로 폭증하는 코드는 관리하기 매우 어려움 -> 즉 모든 기능 조합에 대응하려 하지 마라
- 다음의 특정 기능을 추상화 하는 것은 매우 장황(Overboard)해질 수 있음
	- 메모리 할당 -> VMA, D3D12MA를 학습하고 추상화
	- 자동 resource barrier 삽입
	- descriptor set 관리
	- 초기화 및 하드웨어 선택(device 생성을 의미하는 듯)
	- swap chain 관리
	- 자원 upload 관리
	이들 각각의 추상화는 매우 어려운 주제임. 각 항목이 거의 1년을 들이게 만들 수 있음.
	따라서 결코 과하게 집중하지 말아야 함. 꽤 유용한 수준에는 이를 수 있어도, 정답은 없다.

- **정확하게 목표로 하는 응용프로그램이 필요로 하는 만큼만 추상화 하기**

### 선택장애
절대 완벽한 답은 없다. "충분히 좋은"이면 족하다.

- 같은 동작을 수행하는 정말 많은 방법이 존재하고, 여기에는 정답이 없다. 완벽함이 없다.
- 여러 솔루션이 있다면, 직접 사용해보고 결정해라. 대부분의 경우는 절대 미리 알 수 없다.
- 대표적인 예시가 메모리 관리 부분임. push constant로 상수 업로딩하건 gpu memory mapping을 하건 upload buffer를 써서 중간 버퍼 복사를 수행하건... trade off가 존재하며 상황에 따라 적절한 방법이 달라진다.

### Multi queue
명령을 제출할 queue를 여럿 두지 마라.

일단 한 개로 시작한 다음, 실제로 필요가 발생하면 둘 이상으로 늘리면 됨.

큐에는 종류가 여럿(그래픽, 컴퓨트, 메모리 전송)  있다는 부분을 고려하면, 모든 작업을 다 수행할 수 있는 graphic queue 오직 하나를 고려하는 것이 좋아보임.

특히 동기화 호출로 인한 문제가 생길 수 있으므로, 굳이 시도하지 마시오.

### 객체 생애 주기 관리

"사용중"인 객체의 상태를 변경하는 것은 매우 위험함

이는 모던 그래픽 api의 공통된 문제로, 해당 자원이 CPU와 GPU 동시에 사용되기 때문임.

따라서, 제출된 객체는 "사용중"상태가 되는데, 이게 언제 풀릴지는 GPU마음이라 함부로 소멸하면 안됨. 동기화 솔루션(fence 등)이 필요함.

이 동기화를 내가 수행해야 함.

즉, frame 동기화는 절대 사용해선 안되며, 정말정말 제한적으로만 사용해야 한다.

resource barrier나 fence를 활용한 동기화만 답이다. -> 그래서 RHI layer를 분리해서 별도 thread로?

### 객체지향 문제
모던 그래픽 api는 객체지향하지 않음.

일부 유사한 개념을 가지고 디자인 된 부분이 존재하기는 함.

하지만 100% 일치하지는 않으며, 필연적으로 undefinede behavior가 발생하게 됨.

특히 객체 생애 주기를 RAII로 관리하려고 시도하면, cpu와 gpu 타임라인 불일치로 문제가 될 것임.

이를 해결하기 위해서 비동기 자원 관리 매니저, 혹은 deletion queue를 고려할 수 있음.
-> resource manager?

즉, 소멸자 호출 시 해당 자원을 deletion queue에 등록하고, 해당 큐에 등록된 자원은 비동기 큐에 의해서 해제된다던지...

### Frames in Flight
CPU와 GPU를 프레임 단위로 동기화 하는 것은 매우 지양해야 할 일이라 함.

따라서, CPU는 작업을 큐에 제출한 후, 먼저 다른 frame을 작업하러 이동해야 하며, 

이 과정에서 큐에 제출했지만, 아직 GPU가 소비하지 못한 중간 자원들이 여러 frame 발생함.

이 각각의 frame에 필요한 자원을 multi-buffering한다고 하고, 이 것이 frames in flight임

즉, 큐에 제출한 것을 in flight, 그리고 이러한 프레임이 여럿 존재하여 frames

하지만, 이러한 버퍼를 무지성으로 여럿 유지하는 것은 상당한 비용으로 이어짐.

따라서 반드시 필요한 부분만 구분하여 multi-buffering해줘야 함.

선행할 수 있는 frame의 수는 대략 swap-chain의 수 만큼이라 할 수 있음.

이 부분은 모던 그래픽스를 사용하는 핵심 이유이기에 중요하게 다뤄져야 함.
