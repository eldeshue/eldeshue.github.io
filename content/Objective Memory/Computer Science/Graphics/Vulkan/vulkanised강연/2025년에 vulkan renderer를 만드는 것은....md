# Description
2025년 Vulkanised에서 있었던 LunarG의 개발자 charles giessen의 발표 내용의 요약입니다.

렌더러를 구현함에 있어서, 구현 상세보다는 개념적이고 패턴적인 이야기를 다루고 있음.

기본적으로 vulkan은 매우 거대한 api임. 따라서 구체적인 렌더링 알고리즘을 다루지 않을거임.

## 디자인

### 1. API 버젼 선택
네 하드웨어가 지원하는 최소 버젼을 사용하면됨.

대부분의 데스크탑 환경은 1.3을 지원할 것이기 때문에 큰 선택 문제가 아님.(안드로이드는 1.1부터 시작해야 함...)

1.4는 너무 최신이라 지원하는 하드웨어가 없을듯.....

#### 1.1 인스턴스 버젼
현재 가지고 있는 loader의 version, 즉 api 구현체의 버젼을 의미하는 것으로 보임.
#### 1.2 Physical Device 버젼
GPU 디바이스 드라이버의 버젼임, 즉 하드웨어가 지원하는 버젼의 한계
#### 1.3 Application 버젼
현재 응용프로그램이 사용하는 api의 버젼임. 

위 세 항목을 확인하고 선택하면 되는듯?

### 2. extension 선택
#### Device Extensions
하드웨어가 지원하는 익스텐션, 대부분이 코어 기능으로 발전할듯
#### Instance Extension
소수, 디버그 유틸리티, 등 

약 300개가 넘는 ext가 존재하며, 각각은 나름의 문제를 해결함.

네 구현 목적이 구체화될수록 선택 기준이 명확하게 될 것임.

- hardware 지원
- 목표 version
- 실행 환경(win과 linux는 같은 하드웨어도 지원 내용이 다를 수 있음)
- 등등

각 ext를 직접 선택하려면 대단히 복잡하고, 많은 연구가 필요함. 

대안으로 **profile을 추천**함. 이는 **ext의 모음으로, 명시적인 확장 및 기능 요구사항의 preset**임.

일종의 표준 조합을 제안하는 셈.

작업그룹(루나G, 안드로이드, 등)은 나름의 ext 조합과 이들이 제공하는 기능을 profile로 구성, 제공하고 있음. 이를 따르는 것이 일종의 기준이 될 수 있음(이후에는 각자 알아서 추가하면 됨).

## Vulkan 1.0을 추천하지 않는 이유
그렇다면 왜 우리는 이런 복잡한 버젼 관리의 늪에 빠졌는가?

그 이유는 바로 1.0의 구현이 대단히 사용하기 어렵고, 또 문제가 많았기 때문임.

### Pipeline Explosion
1.0의 고전적인 문제 중 하나는 파이프라인의 조합론적 폭발이었음.

렌더링을 위해 pipeline을 구성하기 위해서는 파이프라인에 bind될 자원을 모두 다 알아야 함.

이는 달리 말하자면, 조금의 옵션 변경에도 pipline을 새로이 만들어야 함을 의미함.

따라서 무수히 많은 조합의 파이프라인을 미리 만들어야 했고, 또 어떤 때에는 JIT으로 파이프라인 생성할 때도 있었음.

이는 대단한 부하였고, 그래서 게임에서는 로딩 시간이 존재했음.

이를 해결한 것이 Dynamic state임. 이를 사용하면 파이프라인을 생성하는 시점이 아니라, 파이프라인을 command list에 등록하는 시점에 상태를 결정할 수 있었음. 즉, **파이프라인을 변형**할 수 있게 됨.

이를 위해 존재하는 ext가 바로 GPL와 Shader Object Extension임.
#### Graphics Pipeline Library, GPL
파이프라인을 구성하는 각 단계를 linkable한 작은 binary로 나누어서 bind 직전에 조합할 수 있도록 만드는 ext임.
#### Shader Object
파이프라인 객체를 완전히 없애고, 컴파일 된 셰이더 각각의 stage를 활용함. 추가적 연구 필요.
### Render Pass
- 렌더 패스는 선언적 구조, 이 렌더링 과정 자체를 정의하는 무언가(구조체)임.
- 마치 렌더 그래프처럼, 이 렌더링이 수행되기 위한 입력(이미지 텍스쳐), 출력(백버퍼), 등을 명시하게 됨.
- 일종의 힌트처럼 제공되어 렌더링 과정에서 사용하는 GPU자원 사용을 최적화(타일링) 하게 됨.
- 이를 보고 드라이버가 렌더링 과정 자체를 재배치할 수도 있음.

이론적으로는 매우 좋은 구조지만, 현실에서는 그닥 그렇지 못했던 것으로 보임.

- 한 객체가 여러 책임을 갖게 되면서 복잡도 증가
	- 어태치먼트(참조하는 이미지) 선언
	- 각 어태치먼트에 대한 메모리 배리어(상태 전환 방지 동기화 툴)
	- 각 어태치먼트 입출력 정의
	- **대단히 복잡한 아키텍쳐로 이어짐**
- render pass는 타일링 기반 gpu에 유용했으나, 그렇지 않은 gpu에서도 사용이 강제됨
- 복수의 프레임 버퍼 사용
#### Dynamic Rendering
렌더패스의 문제를 해결하기 위해서 동적 렌더링이 등장함. 1.3 api에서부터 사용 가능. 

VkRenderpass 객체 대신, command list 초기화 할 때, 단순히 일련의 객체 사용을 선언하는 것으로 쉽게 바뀜. 즉, 명령 기록 과정에서 inline되어 함께 수행됨. 이제는 파이프라인의 layout만 맞추면 됨.
### Descriptor Sets
기존의 1.0에서 desc set은 유연성이 부족했음.

이러한 유연성 부족 문제를 해결하기 위해서 몇몇 기능이 확장됨.

개별 기능에 대한 이해가 부족한 관계로, 추후 사용에 있어서 연구 필요함.
#### Desc Indexing
주요 해결 방안, bindless rendering 방식을 지원함. desc 제한도 해제해줌.
#### Descriptor Buffer
디스크립터를 직접 관리하게 해줌, D3D12의 디스크립터 모델과 유사해짐 -> api 통합에 유리할 듯?
### Shader Memory Layout
셰이더의 메모리 레이아웃은 ABI 불일치 문제가 있었음. 이는 CPU/GPU 데이터 전송에 문제가 될 수 있었음.

이러한 문제를 해결한 sclar block layout이 존재함. 이는 **shader의 abi를 C ABI로** 만든 것임.

### Synchronization
이종 병렬 컴퓨팅에서 동기화는 대단히 까다로운 문제였음.

여러 동기화 솔루션이 제공되었는데, 핵심 해결책으로 Timeline Semaphores가 도입됨.

이는 64비트 단일 카운터 값으로 구성된 세마포어임. 큐에 값을 push하는 것으로 동기화를 수행 가능함.

wait for signal 기능을 구현하는 아주 좋은 근간이 되었음.

다만, swap chain과 통합에 있어서 부족함이 존재함 -> **연구 필요**
